# Задача: «flexible width of FST area»

Необходимо предоставить пользователю менять ширину виджета, ответственного за отображение дерева локальной файловой системы (Explorer).
Максимальная ширина = половина рабочей области экрана (колонки explorer + editor).
Минимальная ширина = 0 = полностью скрытый виджет.

Изменение ширины должно осуществляться путём операции "потянуть за специальную маленькую вкладочку, появляющуюся на границе между виджетом ФС и рабочей областью".

## Текущее состояние (из анализа кода)
- Главный layout: `<div class="ide">` с CSS Grid `grid-template-columns: 48px 260px 1fr;` (см. style.css и app.rs: LoadedApp).
- `<ActivityBar/>` (nav 48px), `<Explorer/>` (aside.explorer), `<Editor/>`.
- Ширина explorer жёстко задана в CSS, ресайза нет.
- Нет drag handle, нет сигналов ширины.

## Что сделать
1. Сделать ширину explorer изменяемой:
   - Хранить текущую ширину в локальном `RwSignal` внутри `LoadedApp` (инициализация 260px). Не добавлять в `Workspace`.
   - Применять через CSS custom property на `.ide`: `style="--explorer-width: {w}px"`.
2. Обновить CSS:
   - `grid-template-columns: 48px var(--explorer-width, 260px) 4px 1fr;`
   - Explorer занимает свою колонку (width:100% или полагается на grid).
3. Добавить resizer-элемент (простой div) между `<Explorer/>` и `<Editor/>` в разметке app.rs.
   - На mousedown начинать drag.
   - На document mousemove обновлять ширину (с учётом границ min/max).
   - На mouseup прекращать.
   - Использовать `window.addEventListener` / `remove` (или leptos on: + gloo) — держать просто.
4. Визуал handle'а ("маленькая вкладочка"):
   - На hover над resizer'ом (или зоной стыка) показывать характерный grip (маленький вертикальный "таб" / pill / 3 линии).
   - cursor: col-resize.
   - При ширине=0 explorer скрыт (grid колонка 0), но resizer-колонка остаётся, чтобы можно было потянуть и вернуть дерево.
5. Ограничения:
   - min = 0
   - max = примерно половина (clientWidth - 48) / 2 ; вычислять при drag или ограничивать после.
6. Не требуется: сохранение ширины между перезагрузками страницы, анимации, двойной-клик для reset.

## Не делать
- Не трогать `Workspace`, не добавлять сигналы ширины в state/split.
- Не менять структуру explorer/mod.rs или tree.rs (только layout в app.rs).
- Не затрагивать split-preview, табы, кнопки, контекстные меню.
- Не persist, не конфиг (кроме если в будущем), не новые крейты.
- Не переписывать .ide на flex (по возможности сохранить grid).

## Приёмка
- Потянув за границу, можно плавно менять ширину explorer от 0 до ~половины доступного места.
- При 0 дерево полностью скрыто, но есть возможность потянуть назад.
- Handle/grip виден при наведении на стык.
- Остальной UI (activity 48px, editor) работает без регрессий.
- `cargo test` + сборка затронутых крейтов (в основном ui + бинарь) успешны.
- Не сломаны другие layout'ы (single pane, split pane).

# Дополнительные указания

## Как убедиться в правильности решения:
1. крейты, код которых подвергался изменениям, должны проходить сборку и проверку локальными unit-тестами;

## Как правильно писать код:
1. этап-1: решить поставленную задачу и убедиться в её работоспособности требуемым образом;
   - код необходимо писать простой, понятный и прямолинейный, без сложных абстракций;
   - если логика кода сложная, но позволяет написать простые unit-тесты для проверки, их надо написать;
2. этап-2: когда поставленная задача будет решена, код, созданный и зафиксированный на этапе-1, необходимо отрефакторить согласно правилам записанным в `wiki\prompts\refactoring-rules.md`
   - при организации кода придерживайся стиля той кодовой базы в которую вносишь изменения;
