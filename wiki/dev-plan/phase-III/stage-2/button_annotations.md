# Задача: «buttons annotations»

Добавить аннотации к кнопкам на левой боковой панели, появляющиеся при наведении после 1.5 секунд удержания.
Все аннотации должны быть включены в файл конфигурации (deck_gen_wasm/conf/src/api.rs) для удобного изменения по необходимости.

## Текущее состояние (из анализа кода)
- `DelayedTooltip` (ui/src/tooltips/delayed.rs) уже реализован, использует задержку `conf::ui::TOOLTIP_HOVER_DELAY_MS == 1500`.
- Левая панель — `ActivityBar` (ui/src/bars/activity.rs), рендерит 7 кнопок из `ui/src/buttons/`.
- Все 7 кнопок уже обёрнуты в `<DelayedTooltip text="...">`:
  - DownloadButton, NewGameButton, LoadGameButton, PrepareHtmlButton, PreparePdfButton, SplitPreviewButton, ClearButton.
- Тексты аннотаций сейчас захардкожены строковыми литералами внутри каждого `*.rs` файла кнопок.
- Требование "все аннотации в конфиге" — не выполнено.

## Что сделать
1. В `deck_gen_wasm/conf/src/api.rs` (модуль `ui` или вложенный `ui::tooltips`) объявить константы со всеми текстами аннотаций.
   - Использовать те же английские строки, что сейчас в коде.
   - Сделать их публичными, чтобы кнопки могли импортировать `deck_gen_wasm_conf as conf; use conf::ui::...`
2. В каждом из 7 файлов кнопок заменить `text="..."` на `text=conf::...::THE_CONST`.
3. Ничего больше не менять в логике отображения/задержки.

## Не делать
- Не трогать `tooltips/delayed.rs`, не менять поведение тултипа.
- Не добавлять аннотации на другие кнопки (NewFile/NewFolder — они в хедере explorer и используют `title=`).
- Не вводить runtime-конфиг, не persist, не локализацию.
- Не затрагивать CSS, workspace, explorer, editor, main layout.

## Приёмка
- Все строки аннотаций определены централизованно только в conf/src/api.rs.
- Кнопки читают их оттуда (без дублирования строк).
- Сборка + `cargo test -p deck_gen_wasm_conf -p deck_gen_wasm_ui` зелёные.
- Визуально в браузере: при наведении >1.5с на любую кнопку activity bar появляется тот же тултип, что был.

# Дополнительные указания

## Как убедиться в правильности решения:
1. крейты, код которых подвергался изменениям, должны проходить сборку и проверку локальными unit-тестами;

## Как правильно писать код:
1. этап-1: решить поставленную задачу и убедиться в её работоспособности требуемым образом;
   - код необходимо писать простой, понятный и прямолинейный, без сложных абстракций;
   - если логика кода сложная, но позволяет написать простые unit-тесты для проверки, их надо написать;
2. этап-2: когда поставленная задача будет решена, код, созданный и зафиксированный на этапе-1, необходимо отрефакторить согласно правилам записанным в `wiki\prompts\refactoring-rules.md`
   - при организации кода придерживайся стиля той кодовой базы в которую вносишь изменения;

## Бережливый подход
1. Максимально береги баланс токенов:

   - использовать Web-Search ЗАПРЕЩЕНО:
     - если необходимо, сформулируй в чате запрос на разрешение поиска с описанием какую информацию хочешь найти и для чего она нужна в рамках решаемой задачи;
