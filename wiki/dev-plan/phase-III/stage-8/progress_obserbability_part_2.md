# Задача: «progress observability - part-2»
Необходимо расширить CLI интерфейс крейта `deck_gen` опциональным параметром --threads для команд `html`, `png` и `pdf`.
Данный параметр должен использоваться для распараллеливания процедуры генерации на заданное количество потоков.
Если параметр явно не задан, то по умолчанию используется 1 поток.

## Особые указания №1:
Поскольку для генерации png и pdf через CLI задействуется api крейта prepare_pdf_host, который в свою очередь осуществляет требуемую генерацию через `chrome.exe`, то для распараллеливания процедуры требуется запускать отдельные процессы (не потоки) контроль за выполнением которых должен осуществляться из `deck_gen`.

## Особые указания №2:
Необходимо улучшить консольный вывод в процессе выполнения команды, отражающий статус выполнения конкретной команды для конкретного потока.
Пример реализации:
```
/> deck_gen.exe pdf --game new-game --threads 8
| game     | deck   | action | progress |
|----------|--------|--------|----------|
| new-game | deck-1 | html   | 10%      |
| new-game | deck-2 | html   | 5%       |
| new-game | deck-3 | html   | 50%      |
| new-game | deck-8 | pdf    | 70%      |
| new-game | deck-7 | pdf    | 89%      |
| new-game | deck-6 | html   | 43%      |
| new-game | deck-4 | pdf    | 100%     |
| new-game | deck-5 | html   | 90%      |
```
Т.е. на консоль должна выводиться динамически обновляемая таблица со столбцами:
1. game - имя игры для которой выполняется целевая команда
2. deck – имя игровой колоды для которой выполняется целевая команда
3. action - название выполняемой команды
4. progress – прогресс выполнения команды

Особенности генерации таблицы:
1. таблица должна быть динамической (т.е. должна перерисовываться каждый раз на том же месте не сдвигая консольный вывод вниз)
2. количество строк таблиц должно равняться количеству рабочих потоков
3. ширина каждого столбца должна быть фиксированной:
   - данный параметр должен задаваться в conf.json5 в корне репозитория
   - если текст не влезает в ширину колонки, то он должен обрываться остаточно заменяться на `...`
   - символы разделитель колонок `|` не должны касаться текста → должен быть разделитель `один пробел` (как в примере)

# Что необходимо сделать
Расширить CLI-интерфейс крейта `deck_gen` (в cli.rs) опциональным параметром `--threads N` для команд `html`, `png` и `pdf` (по умолчанию N=1, т.е. последовательное выполнение).

Параметр `--threads` используется для распараллеливания генерации. Для команды `html` — можно прямо использовать потоки Rust (std::thread) с вызовом соответствующей функции генератора. Для `png` и `pdf` использовать потоки Rust которые вызывают отдельный процесс (через prepare_pdf_host, который вызывает chrome.exe) — запускать отдельные процессы `deck_gen` (или внутренний worker) с передачей конкретной колоды (`--game ... --deck ...`); контроль за дочерними процессами (ожидание, сбор вывода/прогресса) — в родительском `deck_gen`.

Улучшить консольный вывод выполняющейся команды: вместо статичных логов после завершения — динамически обновляемая таблица (перерисовка на месте, без сдвига вывода вниз), показывающая статус по каждому рабочему "слоту" (кол-во строк == N).

Таблица содержит колонки (фиксированная ширина из conf.json5):
| game | deck | action | progress |
Ширины задаются в conf.json5 (секция cli или progress), с обрезкой текста `...` при превышении; разделители ` | ` с пробелами вокруг текста как в примере.

Прогресс в таблице заполняется через `ProgressHandler` (из part-1): каждый worker thread/process отчитывается в центральный контроллер, который перерисовывает таблицу (использовать кроссплатформенный способ обновления консоли, напр. терминал escape или простой clear+rewrite для Windows).

При `--threads 1` поведение близко к текущему (но с таблицей из 1 строки). Поддержать quoted имена игр/колод. Все существующие команды без --threads продолжают работать как раньше.

# Дополнительные указания
1. Изменения в коде должны быть минимальными.
2. Запрещено менять существующую архитектуру.
3. Крейты, код которых подвергался изменениям, должны проходить сборку и проверку локальными unit-тестами.
4. О результатах отпишись в `wiki\result.md` в формате `было→стало(почему)` (очисти файл, если там есть какое-то содержимое перед новой записью).
5. если от меня требуются какие-то действия, то пиши их в `wiki\note.md` (очисти файл, если там есть какое-то содержимое перед новой записью).

## Как правильно писать код:
1. этап-1: решить поставленную задачу и убедиться в её работоспособности;
   - первичный код необходимо писать простой, понятный и прямолинейный, без сложных абстракций;
   - если логика кода сложная, но позволяет написать простые unit-тесты для проверки, их надо написать;
2. этап-2: когда поставленная задача будет решена, код, созданный и зафиксированный на этапе-1, необходимо отрефакторить согласно правилам записанным в `wiki\prompts\refactoring-rules.md`
   - при организации кода придерживайся стиля той кодовой базы в которую вносишь изменения;
3. первый и второй этапы должны делаться раздельно, но в рамках одного промпта (решение → проверка → рефакторинг).

## Как правильно проверять работоспособность:
В соседней папке рядом с папкой проекта находится папка Deck Games (`../Deck Games`), где находятся игры на которых можно проверять работоспособность.
