# Задача на доработку №1: real-time отклик при редактировании

Код не менялся. Ниже — варианты, как убрать ощущение задержки (в т.ч. 300 ms).

Важно про текущую схему (иначе решения будут бить не туда):

- **Каретка не ждёт 300 ms.** `AUTOSAVE_DEBOUNCE_MS = 300` — это пауза перед `localStorage`, не перед вставкой символа. Подсветка ждёт `HIGHLIGHT_DEBOUNCE_MS = 150`.
- **На каждый `input` всё равно идёт синхронная работа на main thread:** `vfs.update` → уведомление *всех* подписчиков `RwSignal<Vfs>`: flatten дерева эксплорера, `prop:value` textarea (clone всего файла обратно в DOM), HTML/Markdown preview без debounce, планирование автосейва и syntect.
- Именно этот round-trip «символ → весь VFS → все панели» даёт лаг. Debounce 300 ms его не лечит и при остановке печати ещё и ставит `serde_json` + `localStorage` на тот же поток.

---

# Решение №1: «Локальный буфер открытого файла, VFS не на каждый символ»

Что необходимо изменить:
Сделать textarea источником правды, пока вкладка в фокусе: `RwSignal<String>` (или неконтролируемый DOM) для тела *активного* файла. `on:input` пишет только в этот буфер. В `Vfs` сбрасывать буфер при смене вкладки, blur, явном Save и по короткому idle (один `requestAnimationFrame` / `0 ms` timeout после паузы ввода — не 300 ms на сам ввод). Автосейв читает уже сброшенный VFS и может остаться с паузой 300–1000 ms: это диск, не каретка.

Как скажется на отклике при редактировании файлов:
Ввод идёт как в обычном `<textarea>`: нет clone файла в `prop:value`, нет flatten дерева и preview на каждый символ. Отклик каретки — native.

Чем придётся пожертвовать:
Два источника правды, пока вкладка открыта. Эксплорер/другие вкладки/prepare HTML не видят последние символы, пока буфер не сброшен. Reload до flush теряет хвост набора (если автосейв тоже ждёт flush). Нужна аккуратная синхронизация, если VFS меняют снаружи (rename, paste, load folder) во время редактирования.

---

# Решение №2: «`update_untracked` на вводе + tracked-notify только структуре дерева»

Что необходимо изменить:
Оставить запись в VFS на каждый символ (`write_file`), но через `vfs.update_untracked`, чтобы Leptos не будил эксплорер, preview и автосейв. Отдельный счётчик/сигнал «дерево изменилось» (`mkdir` / rename / delete / copy) для `flatten_tree`. Для подсветки и preview — отдельный сигнал «содержимое активного пути» или редкий tracked `vfs.update` по idle. Не дробить `Node`/`Vfs`.

Как скажется на отклике при редактировании файлов:
Каретка почти native: нет перерисовки дерева и соседних панелей. `write_file` всё ещё заменяет `String` файла — дёшево относительно flatten + syntect + markdown.

Чем придётся пожертвовать:
Легко забыть tracked-notify на структурной мутации — дерево «залипнет». Preview/подсветка отстанут, пока не сделан idle-flush. Скрытые читатели `vfs.with` не увидят правки, пока их явно не подпишут на content-сигнал.

# Решение №3: «Убрать debounce 300/150 и всё считать сразу»

Что необходимо изменить:
`AUTOSAVE_DEBOUNCE_MS = 0`, `HIGHLIGHT_DEBOUNCE_MS = 0`: на каждый символ сразу syntect по всему файлу, `serde_json` всего текстового дерева, `localStorage.setItem`.

Как скажется на отклике при редактировании файлов:
На коротких файлах без открытого preview может казаться «честнее». На реальных `html`/`json5`/`md` — хуже, чем сейчас: тяжёлая работа не откладывается, а встаёт в тот же кадр, что и ввод.

Чем придётся пожертвовать:
Главный поток и квота localStorage на каждый символ. Это прямое противоречие цели real-time. Имеет смысл только как контролька «debounce был не виноват».

# Решение №4: «Неконтролируемая textarea: не гнать `prop:value` из VFS»

Что необходимо изменить:
Сейчас редактор контролируемый: после `input` Leptos снова ставит `value` из `vfs.read_file(…).to_string()`. Это классический источник лага и сброса IME/каретки. Задать начальное значение один раз при монтировании вкладки (`default` / `uncontrolled`); дальше DOM сам держит текст. В VFS писать из `event_target_value` (как сейчас) или по решению №1.

Как скажется на отклике при редактировании файлов:
Браузер не перезаписывает поле на каждый символ — каретка и IME стабильны. Сам по себе не убирает flatten эксплорера и live preview, если `vfs.update` остаётся tracked.

Чем придётся пожертвовать:
Внешняя смена тела того же пути (undo извне, restore session, paste в дерево) не обновит textarea, пока вкладку не перемонтировать (ключ вкладки уже есть). Нужен явный reset при смене `path`.

# Решение №5: «Тяжёлое — только на idle; ввод не трогать»

Что необходимо изменить:
Оставить `vfs.update` как есть, но отписать от него дорогие подписчики:

- эксплорер: memo по *именам/флагам папок*, не по телам файлов (или не подписываться на VFS при `write_file`);
- preview HTML/MD: сейчас **без** debounce — на каждый символ `inline_relative_iframes` / pulldown-cmark; считать после паузы ввода или по rAF, не вместе с кареткой;
- syntect: не полный файл на символ; либо после idle, либо только изменённая строка + хвост (грамматика TextMate зависит от состояния — полный пересчёт на idle проще и честнее KISS);
- автосейв: пауза 300 ms здесь уместна и даже может быть больше (500–1000 ms); к отклику ввода она не должна иметь отношения.

Как скажется на отклике при редактировании файлов:
Каретка быстрее за счёт меньшей работы в том же тике. Подсветка и preview по-прежнему вспыхивают с задержкой после паузы — это уже не «залипание клавиатуры».

Чем придётся пожертвовать:
Live-preview «как в CodePen» не будет. Подсветка отстаёт от текста (оверлей и так под прозрачной textarea — текст читается сразу, цвета догоняют). Эксплорер не отражает длину/факт правки файла (сейчас и не отражает — только структуру).

---

# Решение №6: «Пакет для real-time: №1 + №4 + №5 (рекомендуемый минимум)»

Что необходимо изменить:
1. Неконтролируемая textarea + локальный буфер активного файла (решения 1 и 4).
2. Tracked-уведомление VFS не на символ, а на flush (blur / смена вкладки / idle ~0–16 ms после паузы).
3. Подсветка и preview считаются с этого flush, не с `input`.
4. Автосейв оставить отложенным (300 ms или 1 s) **после flush** — не путать с задержкой ввода.
5. Не объединять `prepare_html`/`pdf`, не трогать меню и activity bar.

Как скажется на отклике при редактировании файлов:
Набор — native. Цвета и preview догоняют на следующем кадре после паузы. Save на диске по-прежнему пачками, без сериализации на символ.

Чем придётся пожертвовать:
Короткое окно, где VFS/preview старше буфера (десятки мс, не 300). Чуть больше кода синхронизации буфер ↔ VFS. Нет посимвольного live-preview.

# Сравнительный анализ всех решений

| | Каретка | Подсветка / preview | Риск рассинхрона | Объём | KISS | Real-time ввода |
|---|---|---|---|---|---|---|
| **№1** локальный буфер | native | после flush | средний (два источника) | средний | да | да |
| **№2** untracked + сигнал дерева | почти native | после idle | средний (забытый notify) | средний | да | да |
| **№3** убрать debounce | хуже на больших файлах | сразу, ценой кадра | низкий | крошечный | да | нет |
| **№4** uncontrolled textarea | native DOM | как сейчас, если VFS tracked | низкий при ключе вкладки | малый | да | частично |
| **№5** idle для тяжёлого | лучше, не native | после паузы | низкий | средний | да | частично |
| **№6** пакет 1+4+5 | native | после короткого idle | средний, управляемый | средний | да | да |

№3 не решает задачу: 300 ms — не задержка каретки, а отложенный диск; снятие паузы вернёт сериализацию в тик ввода.

№4 дёшевый первый шаг, но без №1/№2 эксплорер и preview всё ещё подписаны на каждый символ.

№2 чуть ближе к «VFS всегда актуален» (удобно для Save/ZIP во время набора). №1 чуть проще рассуждать: «пока печатаю — только строка».
