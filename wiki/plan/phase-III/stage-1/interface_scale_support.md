# Задача
Оболочка IDE должна занимать высоту вкладки браузера и не вызывать прокрутку всей страницы. Два конкретных правила:

1. **Activity Bar** (колонка кнопок слева): все кнопки, включая нижнюю `Clear`, видны без прокрутки страницы и без прокрутки самой полосы кнопок. Если кнопок больше, чем высота вкладки при 40×40, **равномерно уменьшить** кнопки/зазоры, чтобы набор целиком влез. Внутренний scrollbar у `.activity-bar` не делать — иначе `Clear` снова окажется «ниже сгиба».
2. **Explorer** (дерево файлов): при раскрытии папки с большим числом файлов скроллится **только** `.tree`, как Explorer в VS Code. Заголовок «Games», кнопки New File/New Folder и строка статуса остаются на месте.

Это не зум интерфейса и не слайдер масштаба. Только вписывание layout в viewport.

## Текущее поведение (факт из кода)
Разметка: `LoadedApp` → `.ide` = ActivityBar + Explorer + Editor (`deck_gen_wasm/ui/src/app.rs`).

`deck_gen_wasm/style.css`:
- `html, body { height: 100%; }` без `overflow: hidden`.
- `.ide { display: grid; grid-template-columns: 48px 260px 1fr; height: 100vh; min-height: 100vh; }` — у неявной строки грида `min-height: auto`, колонки не сжимаются ниже контента → страница растёт, `Clear` уезжает вниз.
- `.activity-bar { display: flex; flex-direction: column; }` + `.activity-spacer { flex: 1; }` — Clear прижат к низу **полосы**, но полоса растягивается вместе с контентом страницы.
- `.explorer { display: flex; flex-direction: column; }` без `min-height: 0`.
- `.tree { flex: 1; overflow: auto; }` — скролл дерева задуман, но не работает, пока explorer не ограничен по высоте.
- Editor (`.editor`, `.editor-body`, `.editor-split`) уже с `min-height: 0; height: 100%` — не ломать split-preview.

Разметка Explorer: `aside.explorer` → title → header → `div.tree` → `footer.status` (`deck_gen_wasm/ui/src/windows/explorer/mod.rs`). Новые обёртки не нужны, если CSS починит flex.

## Что сделать
В `style.css` (предпочтительно только CSS):
- Зафиксировать оболочку: `html, body` и `.ide` = высота вкладки (`100vh` / `100dvh`), `overflow: hidden` на оболочке, не на `.tree`.
- Всем колонкам грида `.ide`: `min-height: 0; min-width: 0; overflow: hidden`.
- `.activity-bar`: `min-height: 0; overflow: hidden; height: 100%`. Кнопки сжимаются (`flex-shrink`, `aspect-ratio: 1`, уменьшаемый `gap`), пока весь столбец включая Clear виден. Spacer по-прежнему толкает Clear вниз, когда места достаточно.
- `.explorer`: `min-height: 0; height: 100%; overflow: hidden`. `.tree`: `flex: 1; min-height: 0; overflow: auto`. Title/header/status — `flex-shrink: 0`.
- Не менять горизонтальную сетку `48px 260px 1fr`, кроме случаев, когда сжатые кнопки требуют чуть уже/шире колонку Activity — по умолчанию 48px оставить.

Rust-разметку менять только если без нового класса нельзя (не перестраивать компоненты).

## Не делать
- Не добавлять control «масштаб %».
- Не делать `overflow: auto` на `.activity-bar` или `body` как «решение».
- Не переписывать Leptos-дерево окон.
- Не чинить ширину колонок / drag-resize (нет в задаче).
- Не ломать `.editor-split` и preview iframe (комментарий в CSS про PDF plugin).

## Приёмка
- Короткое окно (высота ~400px): страница без вертикального scrollbar; Clear видна и нажимается.
- Длинное дерево (раскрыть `games/` с многими файлами): скролл только в дереве; «Games», New File/New Folder, status закреплены.
- Split preview: обе половины редактора по-прежнему заполняют высоту справа от Explorer.
- Широкий/высокий desktop: визуально как сейчас (кнопки 40×40, spacer, Clear внизу).

***

Баг не в «отсутствии overflow у дерева», а в том, что грид `.ide` растёт вместе с контентом. Сначала ограничить высоту оболочки, потом сжимать Activity Bar и скроллить `.tree`.

# Дополнительные указания

## Как убедиться в правильности решения:
1. крейты, код которых подвергался изменениям, должны проходить сборку и проверку локальными unit-тестами;
   - `cargo test -p deck_gen_wasm_ui --lib`
   - `cargo check -p deck_gen_wasm`
   - визуально: узкая высота окна (Clear видна) и длинное дерево (скролл только `.tree`)

## Как правильно писать код:
1. этап-1: решить поставленную задачу и убедиться в её работоспособнои требуемым образом;
   - код необходимо писать простой, понятный и прямолинейный, без сложных абстракций;
   - если логика кода сложная, но позволяет написать простые unit-тесты для проверки, их надо написать;
2. этап-2: когда поставленная задача будет решена, код, созданный и зафиксированный на этапе-1, необходимо отрефакторить согласно правилам записанным в `wiki\prompts\refactoring-rules.md`
   - при организации кода придерживайся стиля той кодовой базы в которую вносишь изменения;
