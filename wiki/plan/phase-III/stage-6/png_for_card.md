# Задача: «one card one html/pdf»

Необходимо сделать так, чтобы для каждой карты в колоде создавалась png-изображение для лицевой и оборотной сторон.

Важные моменты:
1. уникальные png-изображение для каждой карты должны собираться в рамках специальной папки `<new-game>/_autogenerated/<deck-name>/cards/png/card-N-(face|back).png`
    пример для колоды `deck-1st` в игре `new-game`, состоящей из 4 карт:
    ```
    new-game/
        _autogenerated/
            deck-1st/
                cards/
                    png/
                        card-1-back.png
                        card-1-face.png
                        card-2-back.png
                        card-2-face.png
                        card-3-back.png
                        card-3-face.png
                        card-4-back.png
                        card-4-face.png
                back.html
                back.pdf
                face.html
                face.pdf
                preview.html
                a4-duplex.pdf
    ```
2. для данной команды должен расшириться CLI интерфейс новой командой `png` по аналогии с командами `html` и `pdf`.
3. данная команда должна быть доступна также в сборке для wasm.

# Что необходимо сделать
<Реализовать генерацию PNG-изображений индивидуально для каждой карты (card-N-face.png / card-N-back.png) в cards/png/ внутри _autogenerated/<deck-name>/ .

Расширить CLI новой подкомандой `png` (аналогично `html` / `pdf`): `deck_gen png --game <g> [--deck <d>]` .

Генерация PNG должна зависеть только от HTML (использовать уже готовые per-card *.html из cards/html/ как вход), быть независимой от PDF пути (никакого impose, никакого PdfEngineGenerator).

Команда png (и соответствующий prepare_png_named) должна быть доступна в wasm-сборке (для работы в web-приложении через VFS + JS-растр).>

<По анализу: png-логика будет независимой от pdf. Pdf использует trait PdfEngineGenerator + impose_duplex_bytes в pdf_engine/. Для png:

- png будет опираться на prepare_html_named (или на то, что html уже выполнена, чтобы per-card html присутствовали).
- для каждого card html: растеризовать в PNG (card sized, с учётом CSS) и записать bytes в cards/png/.

В native: используем Chrome (из cli feature / prepare_pdf_host) для загрузки per-card html и capture screenshot (CDP), а не print_to_pdf.
В wasm: используем/адаптируем растеризацию из prepare_pdf_web (html_to_jpeg_pages.js) — можно сделать вывод PNG через canvas.toBlob('image/png').

Pdf код не затрагивается. Html (render) — только prerequisite. Если для raster png понадобится лёгкая прослойка — делаем параллельно без изменения существующих трейтов/архитектуры. "завить" исправлено на "зависеть" (орфография).>

## Как правильно писать код:
1. этап-1: решить поставленную задачу и убедиться в её работоспособности;
   - первичный код необходимо писать простой, понятный и прямолинейный, без сложных абстракций;
   - если логика кода сложная, но позволяет написать простые unit-тесты для проверки, их надо написать;
2. этап-2: когда поставленная задача будет решена, код, созданный и зафиксированный на этапе-1, необходимо отрефакторить согласно правилам записанным в `wiki\prompts\refactoring-rules.md`
   - при организации кода придерживайся стиля той кодовой базы в которую вносишь изменения;
3. первый и второй этапы должны делаться раздельно, но в рамках одного промпта (решение → проверка → рефакторинг).
